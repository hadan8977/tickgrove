# Pine local continuous contract

Supported initial contract is `closed_bar_native`: external callers append explicitly completed OHLCV events to immutable visible-prefix snapshots. The same PineTS 0.11.1 native strategy simulator reconstructs state from source + inputs + that prefix. Historical events are not replayed into a second account or converted into newly invented broker orders. This model can accept genuinely appended market events, persist them, restart and continue. Cost grows with prefix length and the initial runtime limit remains 20,000 bars per sequence.

The service stores pending separately from committed snapshots. Baseline initialization also uses a pending job. A successful transaction commits the new snapshot, authoritative result and event. Failure, cancellation, timeout or interruption leaves the old committed ledger intact. Explicit retry or discard controls failed pending work. Event IDs bind full payload hashes, including after restart.

Each rebuild must preserve every earlier replay-frame value and all closed-trade fields, including entry/exit IDs, bars, prices, quantities, costs and P&L. Earlier open entries must remain identifiable by ID/time/price in the new open + newly closed ledger; partial exits preserve the accounted quantity. Incompatible results fail closed and never replace committed state. Pending orders are retained in the native result. Full tick-by-tick order-intent auditing and broker fill injection remain unverified.

`strategy()` is required for a Pine simulated account. Indicators may run as analysis jobs. Declaration `calc_on_every_tick=true` and `calc_on_order_fills=true` are rejected; explicit false is accepted. Executable uses of `barstate.islast`, `barstate.isrealtime`, `barstate.islastconfirmedhistory`, `lookahead_on` and `varip` are rejected before initialization succeeds; comments and strings do not trigger this diagnostic. Other historical-dependent constructs (for example last_bar_index) are caught by strict rebuild checks when they alter earlier results.

The first append protocol accepts one closed bar per unique symbol and requires a single declared timeframe for all datasets. A multi-timeframe snapshot may be backtested but cannot deploy to continuous mode. This deliberately avoids assigning a primary bar to a different requested timeframe. A future event protocol must identify each symbol/timeframe sequence independently and preserve request.security visibility.

PineTS public type declarations expose `run`, `stream(live)` and `updateTail(Context)`; `update()` is a viewport recalculation, not a new market-event API. The initial product uses deterministic prefix reconstruction rather than claiming a validated long-lived context. It does not claim realtime rollback/varip equivalence. Keeping a live context is an optimization only after matching this persisted reference contract.

External fill feedback is a separate unresolved integration: public PineTS APIs currently provide a native strategy ledger and streaming market-data updates, but no application-level documented broker-execution host contract. Mutating internal strategy state is not a verified feedback bridge. The service therefore exposes `externalFills=false` and never forwards native simulated fills as external orders. Alpaca Paper commands have their own persisted client-order-ID ledger and reconciliation, accessible only with broker.paper scope. Dedicated Paper credentials and a verified bridge are required for end-to-end Pine external execution.

Evidence: `docs/acceptance/local-closed-bar.json`, parent-supervised lifecycle/identity checks, and the public PineTS declarations in `node_modules/pinets/dist/types/PineTS.class.d.ts` and `namespaces/strategy/types.d.ts`. This is an initial local simulation contract, not a TradingView equivalence promise.
