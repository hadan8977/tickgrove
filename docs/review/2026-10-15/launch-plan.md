# Tickgrove 产品达标后的推广方案

2026-10-15 · 状态：方案与文案草稿，未发布。与[产品升级方案](README.md)配套。

**传播机会在于：用户能很快看懂并亲自完成“看图、用自己的 Pine、回测、模拟、扩展”。** 先让这条路径稳定且容易，再把它拍成短视频。Star 是结果指标；长期价值是有人真正安装、反复使用、贡献兼容案例和插件。以下为待验证的增长假设，不是“必然做火”的承诺。

## 定位与第一批用户

英文主描述保持具体：**A self-hosted trading workspace for charts, Pine scripts, and paper trading.**

中文描述：**一个能自己部署、修改和扩展的看盘与策略工作台。**

| 受众 | 最有吸引力的具体任务 | 首次材料 |
|---|---|---|
| 经常使用 Pine、愿意自托管的研究用户 | 导入有权使用的脚本、解释依赖/兼容边界、回测并连续模拟 | 45 秒录屏 + 可直接试用的固定案例 |
| 喜欢控制桌面/服务器环境的开发者 | Docker 启动、数据留在自己的实例、Rust + React、CLI/MCP | 精简快速开始 + 架构说明 + 可运行接口示例 |
| 做多资产规则研究的用户 | 在同一工作台构建组合、回测、检查每次权重变化原因 | 一份可复现的组合教程，避免展示成荐股 |
| 数据/插件贡献者 | 接一个数据源、指标或工具，无需改宿主核心 | 明确扩展合同、最小插件模板、真实需求 issue |

首发集中前两类；不要同时争取所有交易者。核心定位突出自托管、任务连贯和可扩展；复杂的后端事件/授权模型放进工程文章。

可借鉴 [Ghostfolio 的 demo/自托管/文档入口](https://github.com/ghostfolio/ghostfolio)、[NautilusTrader 的明确技术定位与贡献入口](https://github.com/nautechsystems/nautilus_trader)、[OpenBB provider 文档](https://docs.openbb.co/odp/python/installation)。这是发布方式参考，不是这些项目增长的因果证明；当前 Star 数不能证明近期增长。

## 推广前的完成条件

- [升级方案](README.md)中的执行/数据/状态丢失问题修复；广告里展示的市场、时段与 Pine 行为有对应真实验收。
- 原前端权利与根许可证清楚，依赖/测试脚本来源保留。当前仓库证据仍未解决这一点；不能只加一份根 LICENSE 就宣布旧代码已获授权。[GitHub 许可证说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)
- 给新访客一个可立即试用的隔离回放实例：清楚标注示例数据、可重置，不共享管理员 token，不接真实资金，不把个人行情授权直接变成公开数据服务。
- 有经过验收的版本镜像、三步启动、支持的主机说明、简洁的已知限制与兼容矩阵；下载、配置和升级不依赖作者手工救场。
- 新用户测试达到事先定义的成功率；先邀请 10–20 位目标用户试用并收集故障/困惑，重点看首次完成与一周后的自愿回访。人数和目标不是已取得成绩。

项目尚未达标时，可以准备材料、记录研发问题和解决过程；不提前发布“正式版已完成”“完整兼容 TradingView”等承诺。

## 宣传素材包

同一个实测案例生成以下材料，保持版本、数据身份与功能一致：

1. **30–45 秒完整流程视频**：0–5 秒选择标的；5–15 秒导入 Pine 并在同一图表看到结果；15–25 秒打开回测、查看成交；25–35 秒开始模拟并进入该运行；最后展示可自托管和仓库。字幕说明回放/历史/实时及模拟资金。不要通过剪辑掩盖报错和寻找按钮的过程。
2. **一张主要截图**：单图或四图、编辑器、紧凑结果；不把所有功能同时展开。小字、UUID、日志不成为宣传主画面。
3. **一份示例策略包**：有授权的 Pine、依赖、输入、数据来源/许可、预期结果、执行器版本。能通过 Web/CLI 各跑一遍；不以高收益率吸引用户。
4. **一页 Landing/README**：一句话定位、视频、Try demo、Self-host、Features、数据费用/权限说明、兼容范围、贡献入口。README 保持纯英文，中文上手文档单独提供。
5. **开发者材料**：curl/CLI/MCP 的相同命令、插件最小示例、架构/数据设计短文、3–5 个可独立完成的贡献任务。
6. **发布支持材料**：CHANGELOG、常见问题、安装故障诊断、issue 模板、已知问题、隐私说明。不要收集策略源码、交易内容或密钥做增长分析。

## 分渠道内容

| 渠道 | 适合内容 | 发布形式与后续 |
|---|---|---|
| X | 作者视角的产品演示、工程取舍、修复前后操作对比 | 1 条主视频帖 + 少量补充线程，分几天讲一个具体问题；及时回复兼容案例与部署反馈 |
| 小红书 | 桌面看盘体验、怎么导入脚本、如何区分真实行情和模拟账户 | 45–60 秒操作视频或 6 页图文；封面一句用户问题；术语少，数据费用/限制讲清楚，产品名一致便于检索 |
| Show HN | 可实际运行、作者能解释的自托管项目 | 功能达标后集中发一次完整发布，附低摩擦 demo 和仓库，作者留时间回答设计与可靠性问题 |
| r/selfhosted 等自托管社区 | 部署、数据归属、资源占用、备份恢复 | 先核对当日社区规则，再发布具体安装经验；不要复制同一广告到多个社区 |
| V2EX 分享创造、掘金、Rust/前端社区 | 技术实现、解决的难题、明确可用范围 | 用各社区关心的角度写原创文章；按当时版规选择入口，避免一稿群发 |
| 量化/策略社区 | 可复现的方法、数据缺口/回测误差的具体案例 | 只在允许展示项目的板块发布；不把“内容营销”包装成普通讨论 |

[Show HN 规则](https://news.ycombinator.com/showhn.html)要求可尝试的作品，并建议降低注册门槛；不应以仅有 landing page 的预热代替产品。当前 [r/algotrading 规则](https://www.reddit.com/r/algotrading/about/rules.json)明确禁止产品公告和自我推广，因此不列为直接推广渠道。r/selfhosted 等规则需要临发布时再核对，不能把某个旧帖子当作许可。

小红书先定位为软件操作、研究流程和自托管经验；具体外链、商业内容声明与专业内容要求在发布时以账号内规则为准，本次没有取得完整可读取的规则页，不承诺任意导流方式可行。X 使用真实作者/项目身份，内容有实质信息，不采用批量私信、重复评论、互赞或刷指标；这些做法也违反其[真实性规则](https://help.x.com/en/rules-and-policies/authenticity)。

## 首轮节奏

以产品达到发布条件的日子为 D0，避免先定宣传日期再倒逼虚假完成。

| 时间 | 动作 | 观察与下一步 |
|---|---|---|
| D-14 至 D-7 | 目标用户小规模试用、修复最常见卡点 | 安装能否完成、首次图表/Pine/回测成功；保留未完成原因 |
| D-7 至 D-1 | 固定 release candidate、录屏、检查 demo/许可/文档，准备中英文材料 | 换一台干净主机照 README 操作；检查视频每个承诺有证据 |
| D0 | 发布版本与仓库说明，X 主视频；集中处理反馈 | 不同时铺满所有平台；看访问转试用、试用转成功 |
| D+2 至 D+4 | 小红书操作教程、中文部署文章 | 记录普通用户理解障碍，先修入门问题 |
| D+5 至 D+7 | 若核心流程稳定，再做 Show HN/合规社区分享 | 作者及时答疑；出现严重回归先修复并更新状态 |
| 第二周 | 发布一次反馈驱动的小版本；介绍首个真实外部贡献 | 展示具体改进和贡献者成果，而非反复发求 Star 文案 |

## 可直接改写的文案草稿

以下文案只有在对应功能、许可和 demo 验收完成后才能用。

**X 主帖**

> I’m building Tickgrove, a self-hosted workspace for charts, Pine scripts, and paper trading.
>
> Import a script, see it on a chart, backtest it, and follow the paper run in one place.
>
> Rust + React. Extend it through the API, CLI, or MCP.
>
> Demo + source: [links]

补充回复直接列支持的数据源、Pine 兼容范围及当前限制。第一版帖子不写未经测量的“更快”“最准确”“替代全部 TradingView”。

**小红书标题候选**

- 我把看盘、Pine 脚本和回测放进了一个工作台
- 给自己的看盘工具做一次减法：四张图也能看清
- 从一个 Pine 脚本到模拟运行，中间到底要点几下

六页图文顺序：使用中的烦恼 → 完整界面 → 导入脚本 → 看回测/成交 → 模拟与真实资金的区别 → 自托管方式与数据来源/费用。正文讲自己的实际使用过程，不展示盈利承诺。

**Show HN 标题候选**

> Show HN: Tickgrove – A self-hosted workspace for charts, Pine and paper trading

首条说明回答：为什么做、当前已完成哪条路径、如何立刻尝试、核心技术取舍、已知边界、希望收到哪类反馈。复杂脚本兼容问题需要最小脚本/输入/数据来源，不让用户只说“不能跑”。

## 判断是否值得继续放大

观测链路：曝光 → 文档/demo → 第一次成功 → 一周后回访 → 提交可复现问题/贡献。Star、fork、关注数同时记录，但不代替使用成功。

建议第一轮内部目标：20 位目标试用者中至少 15 位独立完成核心流程，至少 8 位一周后主动再次使用；最常见三个卡点有修复记录。它们是决策阈值，不是行业基准，也不是增长预测。体验漏斗不达标时先修产品，再放大曝光。

可用仓库访问/clone 汇总、带渠道标签的 landing 链接、用户自愿反馈和可关闭的匿名完成事件；自托管实例默认不上传行为数据。不用数据商密钥、持仓、策略源码做分析。

长期增长最适合来自可复现的 Pine 案例、可靠数据适配器和小插件：让贡献者不必理解整个系统就能贡献一块，并由持续测试保护它。先维持一个清楚的 issue/discussion 入口，待活跃贡献者确实需要，再新增聊天社区，减少维护负担。
